# 参考转设计契约

用户给出截图、URL、品牌资料、产品笔记或“像这个感觉”并要求形成可复用方向时，使用本文。目标不是写更长的提示词，而是让后续原型和实现不再猜测设计决定。

## 1. 锁定目标

写清目标产物、受众、品牌环境、核心任务、参考范围和技术约束。缺少的信息只有会改变核心方向时才询问；其余标为推断。

## 2. 建立证据表

每项依据标为：

- `provided`：用户明确提供。
- `observed`：从截图、页面或实际操作观察到。
- `inferred`：基于前两者推断，仍需验证。

没有拿到真实画面时，不把记忆写成观察。参考不可访问时说明限制，并换用已有证据或请求补充。

## 3. 拆开参考语义

每份参考分别写：

| 分类 | 内容 |
| --- | --- |
| 保留 | 可迁移的关系，例如密度、构图、字体节奏、色彩温度、动作反馈 |
| 改变 | 当前产品的内容、对象、品牌资产、页面结构和场景差异 |
| 禁止复制 | 标志、专有素材、业务数据、原样界面组合、可能误导来源的表达 |

“做同款”默认指借可控制的关系，不是克隆原产品。精准还原任务例外，但仍按用户授权与目标范围执行。

## 4. 冻结一个连贯方向

写一句最终设计立场，并指出关键取舍。不要为了显得全面同时保留互相冲突的风格。确有竞争方向时，回到 `direction.md` 的显式比较流程。

## 5. 写设计契约

`DESIGN.md` 至少覆盖任务实际需要的部分：

- 产品目标与视觉北极星。
- 色彩角色和具体色值。
- 字体角色、字重、尺度、行高和回退。
- 间距、网格、布局与响应式。
- 组件和控件语法。
- 核心交互、状态和动效。
- 文案与品牌语气。
- 反模式和必须保留的识别点。
- 证据、未知项与验收重点。

需要工程消费时同步 `tokens.css`。Token 使用语义角色，不让 `DESIGN.md` 与 CSS 出现互相矛盾的值。

## 6. 实现交接

交接说明保持可执行：需要读取的文件、不可改变的约束、关键素材、目标视口、核心状态，以及“第一个代表性交付必须证明什么”。设计契约先于原型生成；用户只要契约时，不继续修改业务项目。
