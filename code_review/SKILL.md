# 代码评审

把评审变成可靠的质检环节：系统性分析变更，输出可执行、可证伪的评审结论。

## 适用场景

- 一批改动完成后的独立评审
- 提交 / 发布前的质量把关
- 排查疑似 bug 的变更

## 输入三态

| 输入 | 含义 | 取材方式 |
| --- | --- | --- |
| 工作树 | 未提交的改动 | `git status` + `git diff` |
| 提交区间 | 已提交的某段历史 | `git log` + `git diff <a> <b>` |
| 指定文件 | 只看某些文件 | 直接读文件 + 其 git 历史 |

在仓库所在 host 上经 exec 执行 git 与构建测试命令。

## 评审流程

### 阶段 1：摸面（定范围）

1. `git status` / `git diff --stat` 列出全部变更文件与规模
2. 弄清这批改动的目的：用户说明、变更日志、提交消息或代码注释；目的不明先问
3. 超过 400 行的变更先建议用户拆分，再逐部分评审

### 阶段 2：高层审视（定方向）

- 方案是否匹配问题：有没有更简单或已有的做法被忽略——先搜现有工具函数，再接受新代码
- 文件组织与模块边界是否合理
- 是否混入与主题无关的变更

### 阶段 3：逐文件精读

对每个变更文件：先看 diff，再读变更点周边的完整上下文——不理解意图之前不批评。

### 阶段 4：输出报告

见「输出格式」。

## 检查维度

1. **正确性与边界**：空值、零长度、越界、并发竞态、幂等性、状态机转移
2. **错误处理**：错误是否被吞、资源是否释放（文件 / 连接 / 定时器）、失败路径行为是否明确
3. **安全**：注入（SQL / 命令 / 路径）、越权访问、机密数据落盘或进日志
4. **性能**：N+1 查询、循环内重复计算、内存泄漏、热路径上的不必要分配
5. **测试**：新逻辑有无回归用例；用例是否真实断言而非空转；边界是否覆盖
6. **契约一致性**：接口签名变更与调用方是否同步；前后端 / 双端文件是否对齐；文档、注释、文案与代码一致
7. **可维护性**：命名达意、死代码、重复逻辑、过深嵌套、抽象泄漏
8. **破坏性影响**：数据结构 / 接口 / 行为的不兼容变化是否被识别，处置是否符合项目策略

## 分级

| 级别 | 含义 | 处置 |
| --- | --- | --- |
| P1 | 阻断：bug、安全、数据损坏、契约破坏 | 必须修 |
| P2 | 重要：明显坏味道、缺测试、文档失同步 | 应当修 |
| P3 | 建议：风格、可读性、替代方案 | 可选 |

## 输出格式

    ## 评审报告：<批次主题>

    ### 变更概览
    | 仓库/模块 | 文件数 | 变更摘要 |

    ### Findings
    - [P1] path/to/file:123 — 问题一句话。影响：…。建议：…
    - [P2] …

    ### 总体裁决
    可提交 / 修复 P1 后复审

## 反馈纪律

- 每条 finding 必须给证据：文件行号 + 反例或复现路径；禁止「感觉不对」式批评
- 具体可执行，对事不对人；可用提问式（「items 为空时这里会怎样？」）
- 不挑纯格式问题（那是 linter 的职责）
- 值得肯定的好设计简要指出
- **评审只读**：评审过程不改任何代码，修复是评审之后的独立环节
