# 代码提交

把完成的改动变成干净、可评审的提交：只含预期变更、按逻辑拆分、消息清晰规范。

**执行边界**：AI 负责盘点、验证、拆批、起草消息；**实际执行 `git commit` 前必须把拆批方案与消息草稿呈给用户并取得确认**。`git push` 永不主动执行。

在仓库所在 host 上经 exec 执行 git 命令。

## 工作流

### 1. 盘点

    git status --short
    git diff --stat

- 涉及多个仓库时逐个盘点（同一主题可能横跨多仓库）
- 列出全部脏文件；识别其中与本次主题无关的变更——不混入，单独报告给用户
- 看一眼最近的 `git log`，确认当前分支与基线

### 2. 验证

提交前跑项目的完整验证（入口从 Makefile / package.json / CI 配置找）：构建、静态检查、全量测试。不绿不提交；修复后重新盘点再走流程。

### 3. 拆分

- 一个提交 = 一个逻辑变更；混杂的工作树按逻辑拆成多批
- 文档 / 变更日志与其描述的代码改动同批入库
- 跨仓库的同主题变更：每个仓库各自一条同题提交
- 每批给出精确文件清单，向用户呈报

### 4. 消息

**先看仓库已有风格**：读 `git log` 近十条，仓库已有惯例（语言、格式、type 体系）优先遵循；无惯例时默认 Conventional Commits：

    <type>(<scope>): <描述>

    <正文：为什么改、关键决策、影响面，分点>

    <脚注：BREAKING CHANGE 等，可选>

#### type 表

| type | 用途 |
| --- | --- |
| feat | 新功能 |
| fix | 修 bug |
| refactor | 重构（不改变行为） |
| perf | 性能优化 |
| docs | 仅文档 |
| test | 仅测试 |
| style | 格式调整（不影响逻辑） |
| build | 构建系统 / 依赖 |
| ci | CI 配置 |
| chore | 杂项维护 |
| revert | 回滚提交 |

#### 消息规则

- 描述行 ≤72 字符，祈使语气，说「做了什么」而非「怎么做的」
- scope 取受影响的模块 / 包名，可省略
- 正文解释动机与关键取舍；破坏性变更必须显式标注
- 禁止提交密钥、凭据、.env 类文件——发现即停并报告

### 5. 确认与执行

呈报格式：

    批次 1/2（仓库 a）：<type>(<scope>): <描述>
      文件：<精确清单>
      消息草稿：<完整消息>

用户确认后：

    git add <精确文件清单>     # 不用 -A / .，除非盘点确认工作树无无关变更
    git commit -m "<消息>"     # 多行消息用 heredoc

提交后回报每个仓库的 hash 与消息首行。

## 安全红线

- 禁止任何丢弃变更或重写历史的命令：reset、restore、checkout -- <file>、clean、rebase、push --force、commit --amend（用户显式要求除外）
- 禁止 --no-verify 跳过 hook；hook 失败时修复问题并创建新提交
- 不修改 git config
- 不主动 push；不代替用户做部署 / 重启类操作
